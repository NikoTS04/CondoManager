## Persistencia y secretos

Cabeza nueva: **`20261113_0021`**, hija única de `20261025_0020`.

- `usuarios.activacion_pendiente` distingue el onboarding nuevo de las cuentas
  históricas y de una habilitación manual. Su default es false; no se cambian
  contraseñas, actividad ni privilegios anteriores.
- `invitaciones_usuario` guarda hash, contexto, usuario/creador, revisión de
  permisos y fechas UTC. Los bloqueos de usuario/contextos/invitación serializan
  activación, reenvío y revocación; dos activaciones concurrentes producen un éxito.
- `operaciones_identidad` conserva huella de actor/operación/cuerpo y respuesta
  por condominio y `Idempotency-Key`. Una solicitud repetida compatible devuelve
  la respuesta original; una incompatible recibe conflicto.
- La cola SQL existente se confirma en la transacción de identidad. No hay un
  segundo broker o repositorio de usuarios.
- El enlace viaja en el fragmento `/activar#token=...`, que no se envía al servidor
  web, y se retira de la URL visible. La API solo lo recibe en el POST de activación.
- El token tiene hash en la invitación. El material de entrega en cola se cifra
  con Fernet y una clave externa; DTO, auditoría y cuerpo público no lo exponen.
- El downgrade protege invitaciones, operaciones y avisos de identidad existentes.
  Los ensayos de reparadores legacy se fijaron a sus esquemas históricos; los
  reparadores productivos siguen rechazando una cabeza distinta de su corte.

## Configuración y uso

Instalar las dependencias declaradas y aplicar la migración del ambiente:

```bash
python -m alembic upgrade head
```

Variables de `.env.example`, compartiendo la misma clave entre API y worker:

```dotenv
ACCESS_TOKEN_EXPIRE_MINUTES=60
INVITACION_EXPIRE_HOURS=24
ACTIVACION_WEB_URL=http://localhost:3000/activar
IDENTITY_DELIVERY_KEY=
```

Generar una clave una vez y configurarla en `IDENTITY_DELIVERY_KEY`:

```bash
python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

Docker Compose transmite las variables a los servicios correspondientes. La clave
debe mantenerse durante los reinicios para poder entregar invitaciones pendientes.
Un ambiente sin clave/URL válidas rechaza la invitación con 503 y revierte el alta.

### Recorrido administrativo

1. Iniciar sesión como Junta o SuperAdmin y seleccionar un condominio autorizado.
2. Abrir **Usuarios → Invitar usuario**, completar identidad y enviar. El resultado
   confirma una invitación y correo **EN_COLA**, no recepción.
3. Configurar los vínculos y roles autorizados. Si se modifican durante el onboarding,
   **reenviar al terminar**: el enlace nuevo incorpora la revisión vigente.
4. Consultar el estado de invitación/correo; reenviar la última invitación o revocar
   un enlace pendiente. Reenviar revoca el anterior sin duplicar identidad.
5. El invitado abre el enlace, elige y confirma contraseña e inicia sesión. Sin
   vínculos autorizados puede autenticarse, pero no obtiene acceso a una unidad.
6. Para relevar acceso, seleccionar tipo, saliente, entrante y unidad o rol final
   del saliente. Junta solo se releva desde SuperAdmin. Los dos cambios confirman
   juntos; si se retiró al responsable de pago, configurar después su reemplazo.
7. En **Comunicados**, consultar avisos e intentos. Los avisos de identidad permiten
   reencolado autorizado sin redirigir el destinatario; las aceptaciones inciertas
   requieren revisión del proveedor.

Las API nuevas de invitación y relevo requieren un UUID estable en
`Idempotency-Key` al reintentar. La interfaz conserva esa clave durante el reintento
de la misma operación en la página. La asignación por UUID de identidades existentes
y el contrato HTTP histórico de alta manual se conservan.

## Integración pendiente con CON-78

Finalidades de cola:

| Finalidad | Elegibilidad antes de despacho |
|---|---|
| OPERATIVA | Cuenta, rol, unidad y vínculo activos; sin cambios de sus restricciones |
| INVITACION | Invitación confirmada, pendiente y no vencida/revocada; revisión, cuenta y contexto vigentes; puede no tener departamento |
| SEGURIDAD | Cambio auditado confirmado y contacto del afectado coincidente; puede haber perdido rol o vínculo operativo |

Los productores internos crean los avisos de identidad con `transporte=PROVEEDOR`.
El worker por defecto conserva el simulador y los rechaza con
`PROVEEDOR_NO_CONFIGURADO` y alerta; **no informa un envío ficticio**.

Punto de integración probado: `procesar_uno(session_factory, transport=proveedor)`.
El proveedor recibe una copia de entrega; solo allí se descifra el cuerpo privado,
sin modificar el histórico SQL. La respuesta de aceptación usa `status` 2xx y
`message_id`; ENVIADO no significa ENTREGADO. La clave recibida identifica el
intento; la identidad lógica del aviso sigue siendo su UUID/ciclo.
