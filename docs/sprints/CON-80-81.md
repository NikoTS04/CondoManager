## Ensayo local de respaldo/restauración

Se preparó mediante API real una reserva confirmada, un comprobante con PNG
privado y un aviso con primer intento temporalmente fallido (`REINTENTANDO`).
Sin workers en ejecución se capturaron `public` con `pg_dump --format=custom` y
el directorio privado de vouchers con sus checksums SHA-256.

Se restauró en **otra base vacía** usando `pg_restore --exit-on-error
--single-transaction --no-owner --no-acl` y en otro directorio de archivos.
PostgreSQL crea `public` por defecto: fue necesario retirar ese esquema vacío
**sin CASCADE** antes del restore; el runbook incluye esa precondición.

Se comprobó:

- Readiness, login y mismo UUID/estado de reserva.
- Descarga autenticada del mismo voucher con SHA-256 idéntico; otro residente
  recibe 403.
- Mismo aviso e intento pendiente restaurados; recuperación repetida del outbox
  no duplica avisos. Los eventos de pago aún no consumidos generan sus avisos.
- Dos consumidores concurrentes completan el reintento del aviso original una
  sola vez; queda `ENVIADO`, dos intentos históricos en total y nada reenviable.

Artefactos privados de ensayo en `/tmp/opencode/con80-81-recovery/`; son datos
sintéticos locales, no un respaldo de Supabase. El transporte fue SIMULADO.
Este ensayo no sustituye el respaldo consistente de base **y volumen reales**.
